VeriTrail 0.13.0 是一次有界公共能力发行：它把 `v0.12.2` 以后已经分别实现、验证并冻结的通用
Acceptance Core API 放入新的发行身份。它不新增验收语义，也不把 GitHub Evidence 插件并入 Core。

## 新的公共能力

公开 wheel/sdist 包含：

- `AcceptancePlan` 的验证、封存与 observation/evidence binding；
- sufficiency、integrity 与 assertion 三类确定性求值；
- `PASS / FAIL / INCONCLUSIVE / PENDING` 四 Verdict；
- Acceptance report 与 Bundle 的生成和复验；
- P3 使用的 `ImportedEvidence` snapshot 公共入口，使同一已验证快照被 Core 消费；
- 自 `v0.12.2` 后已经独立闭合的 Browser lifecycle/cancellation 修正。

上述能力在源码中早已存在，但公开 `v0.12.2` wheel 不包含 Acceptance 模块。0.13.0 使用新版本坐标
关闭该 publication identity mismatch；历史 `v0.12.2` 标签、Release 和资产保持不可移动、不可重制。

## 保持不变的边界

0.13.0 不改变：

- Evidence 0.1 与既有 ExperimentPlan/Report/Catalog 的历史语义；
- Acceptance 的四 Verdict 优先级；
- P1/P2 GitHub API/Public Render facts；
- P3 thin manifest 与 snapshot continuity；
- Starter、Authoring Skill、Workbench 的权限边界；
- Core 不认识 GitHub、插件不拥有 Verdict 的依赖方向。

Core `0.13.0` 的发布不表示 Starter 0.2.0 支持 0.13.0。Starter 的已发布 metadata 与运行时守卫都明确
限定 `>=0.12,<0.13`；C1 必须证明它在候选 Core 上以 `CORE_INCOMPATIBLE` fail closed，并在独立环境
使用公开 Core 0.12.2 完成既有正向回归。Authoring Skill 0.2.0 的真实 DRAFT 链依赖 Starter，因而也在
该公开 Core 0.12.2 通道验证；只在候选 Core 上运行静态合同测试不能证明端到端兼容。GitHub Evidence
0.1.0 的源码前向兼容探针与其尚未更新的精确 distribution 依赖是两份证据；后者只能在 0.13.0
公开发布并读回后由 P4 修改。

## 候选与发布验证

C1 已从冻结合同后的 exact main 建立候选，并串行完成：

- Python 3.10 / 3.13 的 normal 与 `-O` 全回归；
- wheel 与 sdist 的仓库外 clean install；
- Acceptance 四 Verdict 与同一 imported snapshot 纵向门；
- Starter/Authoring Skill 的 Core 0.12.x 历史兼容通道与 GitHub Evidence 的明确标注源码前向兼容探针；
- Workbench tests、lint、type-check、build 与依赖审计；
- Browser Smoke、Windows 生命周期与零残留检查；
- 候选 PR 原始 Public CI。

上述候选证据没有冒充最终公开资产；C2 随后从新的 exact main 重新构建并独立验证最终字节。
