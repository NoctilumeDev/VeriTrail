# Post-M8 收束路线 Plan v1

> 状态：`DRAFT / UNFROZEN`
> 影响层级：`L3_SYSTEM`（仅规划，不修改代码、Schema、裁决或冻结标签）
> 前置基线：M0–M8 均为 `FROZEN`，最新冻结标签为 `m8-v0.9.0`
> 实施门禁：本文未冻结前，不开始任何后继里程碑实现

## 1. 产品判断

VeriTrail 是本地优先、资源感知、证据优先的**验证脚手架**，也是一个**认知放大器**。
它把原本隐含在操作者脑中的变量、控制组、不变量、停止线、失败事实和结论边界，转换为可重复、
可审计、可证伪的实验过程。

它不会自动产生正确认知。错误的变量选择、遗漏的不变量或过宽的结论，同样会被稳定地放大。
因此 Post-M8 的目标不只是“能运行更多命令”，而是让真实项目执行仍然服从 M0–M8 已证明的
方法论和安全边界。

必须持续成立的认知护栏：

- 严格区分 `OBSERVED`、`INFERRED` 与 `NOT_PROVEN`，不得把调度计划写成运行事实；
- 计划、断言、停止线和裁决规则必须先于观察冻结；观察后修改必须产生新版本；
- 失败、反例、中止、污染和未解释异常必须保留，不能只归档成功路径；
- AI 可以解释、聚类或建议下一步，但不能决定确定性 `PASS / FAIL`；
- 结论必须携带代码、环境、资源、适用范围和未知项，不能脱离证据包单独传播；
- 工具自身的资源和采集扰动必须与被测对象分开记录。

## 2. 当前事实与剩余缺口

M0–M8 已证明从 sealed Plan 到全因子批次派生分析的本地纵向链路，但还没有证明 VeriTrail
能够安全接管一个普通项目从冷状态到验收结束的完整生命周期。

Post-M8 的主线缺口是：

1. **受控项目命令执行**：当前只有内置 `STATIC_HTTP`，没有 npm、Maven、Python、Docker
   等项目命令的结构化执行能力；
2. **完整项目自举**：当前轻量自举只覆盖 VeriTrail 自身目录，不覆盖项目发现、依赖准备、
   服务启动、就绪、恢复和逆序清理；
3. **真实项目全链路**：尚未用一个不同于测试夹具的项目贯通预检、执行、浏览器、多实例、
   裁决、归档和清理；
4. **前端终稿**：当前主题已形成方向，但还没有完成全局色彩、留白、状态语义、响应式和
   无障碍收束；
5. **系统与代码终审**：尚未在完整能力形成后，从所有者、消费者、状态机、数据流、失败边界
   和爆炸半径俯瞰整个系统；
6. **终局复验**：尚未在整改后的候选版本上完成冷启动、代表性真实链路和无残留收束。

计划编辑器、在线写、远程执行、生产集群编排、统计显著性和 AI 裁决不是本路线的默认目标。
如需纳入，必须单独上浮范围并重新评审，不能借前端收尾或命令执行顺手加入。

## 3. 总体顺序

```text
P0 规划与系统设计门
  -> M9 受控项目命令执行
  -> M10 完整项目自举
  -> M11 真实项目功能全链路
  -> M12 故宫主题前端终稿
  -> M13 系统思维与分层代码质量终审
  -> M14 整改后终局复验与发布收束
```

M9–M14 是 Plan v1 的候选编号，不代表已经开始或承诺实现。只有 P0 冻结后，才逐个建立独立
合同；每一里程碑必须完成代码事实、自动化、真实运行、适用的浏览器/多实例、安全与清理证据，
并冻结为可寻址基线，下一里程碑才能进入实现。

前端视觉规范可以提前规划，但 M12 的实现必须等待 M11 功能事实稳定。这样可以先固定视觉语法，
又不会为了装修界面而反复改动尚未收束的生命周期和数据语义。

## 4. P0：规划与系统设计门

P0 只产生合同和验收矩阵，不产生运行代码。进入 M9 前必须冻结：

- Post-M8 的目标、非目标和术语；
- 受控命令的信任边界、威胁模型与允许列表语义；
- 项目自举的生命周期状态机、所有权和清理责任；
- 首个真实目标项目和第二种不同类型项目的选择标准；
- 16 GB Windows 主机的资源预算、串行默认和微并行上限；
- M9–M14 各自的正向、反向、故障恢复和退出矩阵；
- 故宫主题的 CSS 设计合同与无障碍底线；
- 系统终审、代码质量审查和最终发布的停止条件。

P0 冻结前允许修改本文；冻结后若改变命令信任模型、自举状态机或最终结论语义，必须创建
Plan v2，不能静默改写 Plan v1。

## 5. M9：受控项目命令执行

### 5.1 目标

让不同项目能够声明并运行自己的构建、静态检查、测试和一次性任务，同时保持结构化、可预览、
可中止、可脱敏、可追溯和可清理。

“任意项目命令”表示**项目可以登记不同工具和参数**，不表示 VeriTrail 接受无约束 Shell
字符串。

### 5.2 最小合同

一个命令声明至少需要包含：

- 稳定命令 ID、用途和所属项目 Profile；
- 可执行文件引用与参数数组，禁止用字符串拼接替代参数边界；
- 受项目根目录约束的工作目录；
- 允许读取的环境变量名称；秘密值只透传，不记录、不回显；
- 超时、预期退出码、最大输出和资源停止线；
- 一次性任务或长运行服务的显式类型；
- 中止、进程树回收、证据保存和清理策略；
- 执行前结构化预览及 sealed Plan 绑定。

### 5.3 安全不变量

- 默认拒绝 Shell 字符串、命令替换、未解析变量和根目录外工作目录；
- 默认拒绝未登记可执行文件及未经预览的参数变化；
- 不持久化 `.env` 值、令牌、Cookie、认证头、私钥或个人绝对路径；
- 中止必须终止本次拥有的完整进程树，不能误杀无关进程；
- 清理只能作用于本次 Run 明确拥有并已核验的资源；
- stdout、stderr、退出码、时序、资源与脱敏动作都进入 Manifest；
- 资源停止只产生 `ABORTED` 或 `PENDING`，不能伪造 `PASS / FAIL`。

### 5.4 冻结出口

- 至少两种不同命令家族完成真实正向运行；
- 覆盖超时、非零退出、输出超限、秘密回显拦截、工作目录越界和用户中止；
- 每条异常路径均形成证据并确认进程、端口和临时资源清理；
- 旧 M0–M8 Bundle 与 CLI 兼容回归通过；
- 不在 M9 顺手加入服务依赖图、Docker 编排或在线命令编辑器。

## 6. M10：完整项目自举

### 6.1 目标

在 M9 受控执行之上，把项目从已声明的冷状态推进到可验收状态，并在成功、失败或中止后恢复到
可解释的清洁状态。

候选生命周期：

```text
DISCOVERED
  -> PREFLIGHTED
  -> PREPARED
  -> DEPENDENCIES_READY
  -> SERVICES_READY
  -> EXERCISED
  -> EVIDENCE_FINALIZED
  -> TEARDOWN_COMPLETE
```

任一阶段都可以进入 `ABORTING -> EVIDENCE_FINALIZED -> TEARDOWN_COMPLETE`。失败不能跳过证据
封存，证据封存也不能阻止尽力清理。

### 6.2 所有权与适配器

- 项目 Profile 声明所需工具、端口、服务、就绪条件、依赖顺序与回收顺序；
- 自动发现只能提出候选，执行前必须形成可查看的确定性计划；
- 本地进程、Docker 或中间件必须分别使用明确适配器，不能全部退化成 Shell；
- 只停止当前 Run 创建或明确接管的资源，不接管来源不明的既有服务；
- Docker 适配器不得全局清理镜像、卷、网络或其他项目容器；
- 就绪必须使用有界健康检查，不能把“进程存在”当成“服务可用”；
- 逆序回收后检查进程、端口、容器、临时目录和连接残留。

### 6.3 资源策略

- 每次运行重新采样内存、磁盘、端口和相关运行时，不能照搬机器档案快照；
- 默认串行；微并行必须声明 wave、总预算、互斥资源和停止条件；
- M8 的 wave 只是调度语义，不能作为 M10 真实重叠运行已经成立的证据；
- 超过软阈值停止升压，超过硬阈值立即保存现场并中止；
- VeriTrail 自身资源与被测项目资源分别记账。

### 6.4 冻结出口

- 从冷状态完成一次成功自举、一次中途失败恢复和一次用户中止恢复；
- 证明就绪检查、逆序清理、端口竞争和已有外部进程保护；
- 第二次运行不受第一次残留污染；
- 真实重叠运行只在预算允许的最小 wave 中证明，不宣称生产容量。

## 7. M11：真实项目功能全链路

### 7.1 目标

用真实项目证明 VeriTrail 不只会验证自己的夹具。目标项目必须在实施前按类型、资源、可重复性、
浏览器链路和失败注入能力登记；不能因为某个项目更容易通过而在观察结果后更换。

至少需要两层目标：

- 自身最小目标：用于快速证明执行器和自举基本闭环；
- 不同类型的真实目标：用于排除“VeriTrail 只适配 VeriTrail”的自证循环。

具体仓库要经过只读适配性盘点后写入 M11 合同，本文不预先假定项目技术栈。

### 7.2 代表性完整链路

```text
实时环境与资源预检
  -> sealed Plan 与命令预览
  -> 项目完整自举
  -> 构建 / 检查 / 测试 / 服务生命周期
  -> 桌面与移动浏览器真实操作
  -> Console / Network / 关键业务事实
  -> 适用的多实例、重试、故障与恢复
  -> 确定性 Verdict
  -> Comparison / Paired / Batch 派生分析
  -> 证据归档与哈希
  -> 逆序清理与残留确认
```

### 7.3 冻结出口

- 成功链、业务失败链、基础设施失败链和恢复链全部真实运行；
- 浏览器检查关键交互、失败重试、桌面/移动、Console 与 Network；
- 涉及多实例或一致性时核对权威事实、重复副作用和恢复结果；
- 失败事实与成功终验共同保留；
- 复跑能够解释稳定项、差异项和仍未证明项；
- 16 GB 资源不足可以形成 `PENDING`，不能降低一致性或安全标准。

## 8. M12：故宫主题前端终稿

### 8.1 实现原则

- 使用 HTML/CSS 和现有组件体系构造，不贴背景图、不用位图纹理模拟建筑；
- 中国式留白依靠结构、比例和虚实关系，不用整体降对比、灰雾化或柔焦制造“东方感”；
- 色彩允许内部张力，避免把全部明度、饱和度和色温压成单一的日韩式现代极简模板；
- 视觉修改不得重新解释 Verdict、Schema、状态机或证据所有权。

### 8.2 状态色语义

- 宫墙朱红：仅用于失败、异常、故障断点和危险操作；
- 琉璃鎏金：用于运行中、加载中和正在校验；
- 玉白：主背景、正文与只读证据区域，保持明确白度而不是雾灰；
- 黛青：导航、边界、分区轴线与次要控件；
- 成功、待定、中止和不可归因必须同时有文字、图形或纹理差异，不能只靠颜色。

### 8.3 布局与验收

- 总览、链路详情、原始证据/归档形成层层递进但不过度拟物的院落式层级；
- 留白服务于信息分组和阅读节奏，不能以减少必要事实为代价；
- 键盘顺序、焦点环、语义标签、减少动画和屏幕阅读保持有效；
- 对比度至少满足 WCAG AA 的适用要求；
- 真实检查桌面与移动视口、缩放、长文本、空状态、错误状态和加载状态；
- Codex 内置浏览器完成完整用户链，DevTools Console/Network 无未解释异常。

## 9. M13：系统思维与分层代码质量终审

系统思维审查设置两道门：P0 在实施前检查方向和边界，M13 在能力形成后检查真实系统。前者避免
走错路，后者防止每个模块局部通过却没有形成可靠整体。

### 9.1 系统审查维度

- 产品目标、非目标和真实用户链是否仍一致；
- Plan、Run、Evidence、Verdict、Catalog 与三类派生分析的所有权和数据流；
- 命令、自举、浏览器、资源与清理状态机是否存在绕过路径；
- 失败、重试、中止、崩溃恢复和部分成功是否都有唯一且可解释的语义；
- 安全边界、秘密流向、工作目录、进程树、端口和 Docker 所有权；
- 单机资源预算是否贯穿计划、运行、分析和 UI；
- 冻结合同、兼容策略和迁移路径是否仍能被旧消费者使用；
- 是否出现为了“通用”而复制 CI、容器平台或生产编排器的问题。

### 9.2 分层代码质量审查

- `L0 表现层`：语义、可访问性、渲染性能和前端状态边界；
- `L1 组件内部`：职责、错误处理、测试质量、资源释放和可维护性；
- `L2 公共契约`：Schema、序列化、兼容性、消费者和迁移；
- `L3 系统级`：状态机、跨组件不变量、信任边界、爆炸半径和恢复能力。

审查发现先按严重性、所有者和影响面归档，再决定最小整改范围。不得为了统一风格进行无关的
全仓重写；跨层整改必须列出全部消费者并复跑对应矩阵。

## 10. M14：整改后终局复验与发布收束

M14 不增加功能，只验证整改后的候选版本并形成最终结论。

必须覆盖：

- 近似干净环境下的安装、冷启动和完整自举；
- 一个自身目标和一个不同类型真实目标的代表性完整链路；
- 浏览器桌面/移动、键盘、Console/Network 和失败恢复；
- 适用的受控微并行、多实例、重复、超时、中止和恢复；
- Bundle 重建、哈希、Catalog、Comparison、PairedAnalysis 与 BatchAnalysis；
- 全程资源曲线、软/硬停止线和最终无残留；
- 安装、使用、安全、限制、故障排查和里程碑历史文档；
- 代码、标签、发布产物和远端仓库的一致性回读。

最终报告只能在证据范围内声明完成。任何必需链路因资源、权限或外部状态无法运行时，项目状态
保持 `PENDING`，并明确列出已完成实现、局部证据与待执行终验。

## 11. Plan v1 冻结条件

本文只有同时满足下列条件才能从 `DRAFT` 进入 `FROZEN`：

- 用户确认 Post-M8 的顺序、范围和非目标；
- M9 结构化命令合同没有 Shell 后门或含糊的资源所有权；
- M10 生命周期的每个失败出口都能进入证据封存和清理；
- M11 真实目标选择规则不会形成自证循环；
- M12 视觉合同明确区分中国式结构留白与整体雾化，并锁定状态色语义；
- M13 审查层级与整改回归责任明确；
- M14 终局标准没有用局部测试代替用户可见完整链路；
- 全部阶段均遵守 16 GB 主机的串行或受限微并行边界。

冻结 Plan v1 只是允许 M9 开始，不代表 M9–M14 已实现或已经验收。
