# 工程活性、目标连续性与全局进展反思

> 性质：设计反思 / post-R1 全局检查输入
> 不构成：新合同、新门禁、R1 状态发布、runtime 实现授权，或对既有冻结历史的重解释
> 使用时机：当前 R1 按既有授权与资格链闭合以后，独立进行全局组合检查时

本文使用的“应当”“必须”和大写终态名称都只表达待审议的问题与概念占位符，不是当前公共 Schema、
状态机、qualification vocabulary 或自动调度规则。任何一项若要成为工程约束，仍须另行取得明确 owner、
合同、反例、兼容边界与施工授权。

关联材料：本反思补充[证据反馈工作法](working-method.md)没有直接回答的全局活性问题，并以
[能力边界与系统认知地图](114-capability-boundary-and-system-map.md)中的产品目标、authority 与候选能力边界为背景。
两份关联材料都不能被本文修改或扩权。

## 1. 为什么要保留这份反思

VeriTrail 已经建立了严格的事实、证据、资格与授权边界。这些边界解决了一个根本问题：不能把“执行过”“测试通过”或
“模型声称已经修复”当成现实中的完成事实。

但严格的局部闭环还留下另一个同样根本的问题：

> 一个系统可以不断正确地处理局部失败，却始终没有完成用户最初交给它的工程任务。

这不是简单的死锁，也不一定是某个模块的实现错误。它可能是一种**战略性不终止**：每一步都有理由，每一步都符合某个局部
规则，系统却在恢复、补证、再资格化与重新投影之间持续循环；局部证明越来越多，业务目标并没有相应接近。

因此必须同时保留四个判断：

```text
Execution is not truth.
Proof is not progress.
Safety is not liveness.
Non-execution is not success.
```

前三句防止把活动、证明和安全误写成任务完成；最后一句防止为了避免风险而把永久不行动包装成成功。

## 2. 从“毒披萨”问题看到的缺口

如果一个进程或 Agent 面对“是否吃掉一块可能有毒的披萨”，仅以避免错误为目标，最安全的局部策略可以是永远检查、永远
等待、永远补充条件。这样确实减少了做错的概率，却没有回答任务是否必须在有限时间内得到一个可接受的终态。

这类问题的关键不是“检查得够不够仔细”，而是目标函数里是否同时存在：

- 必须保持的安全与真实性约束；
- 必须推进的业务目标；
- 明确的时间、资源与恢复预算；
- 预算耗尽后的合法终态；
- 只有人类可以作出的目标、风险与继续投入决定。

如果只奖励局部正确、局部纠错或局部证明，Agent 很容易发生目标漂移：它逐渐把“避免再次犯错”“让下一道门变绿”或
“解释为什么尚未完成”当成任务本身。

## 3. 局部正确不自动组成全局正确

VeriTrail 的模块可以各自在自己的合同内保持正确，但这不自动证明组合后的控制平面具有全局活性。

```text
局部合同成立
    + 局部测试通过
    + 局部资格闭合
    != 用户的工程问题已经解决
```

同样，理论遇到反例时应先检查前提和模型边界，而不是不断增加例外。这个原则既适用于一个局部合同，也适用于整个系统：

- 如果局部恢复链反复出现，先检查全局调度前提是否成立；
- 如果每次恢复都生成更多待闭合义务，检查恢复机制是否正在扩大问题；
- 如果证明越来越完整而产品目标没有推进，检查当前证明对象是否已经偏离原问题；
- 如果一个局部 PASS 需要依赖另一个尚未拥有权威的世界，不能用更多拼接掩盖前提不成立。

形式推导可以完全正确地回答一个错误的问题。工程系统也可以完全正确地闭合一条已经偏离业务目标的资格链。

## 4. 业务目标与硬约束不能互相替代

这里不能走向另一个极端。业务目标重要，不代表它可以覆盖真实性、安全性或授权边界。

更准确的关系是：

- **业务目标是优化对象**：系统应当持续减少尚未履行的真实产品义务；
- **真实性、证据完整性、安全性与 authority 是硬约束**：不得为了更快宣称完成而伪造、拼接或越权；
- **时间与资源是显式预算**：不能假设无限重试、无限补证或无限恢复；
- **人类保留目标与风险决定权**：Agent 不得自行改写“完成”的含义，也不得把无法完成静默改写为无需完成。

因此总原则不是“业务优先，所以门禁可以跳过”，也不是“门禁优先，所以业务可以永远不完成”，而是：

> 技术复杂度不能代替业务目标；业务目标是优化对象，真实性、安全性与授权边界是硬约束。

## 5. 资格失败不应自动成为项目调度器

资格链负责回答某个声明是否已经在声明的坐标上成立。它不应自动决定整个项目下一步必须做什么。

一次失败可能意味着：

- 产品或实现真的击穿了冻结边界；
- 测试或观察设施存在问题；
- 外部环境暂时不可用；
- 当前证据不足，底层原因仍为 `UNKNOWN`；
- 当前任务不再值得继续投入，但这需要人类决定。

只有第一类事实能够直接支持重开相应产品边界。其余情况必须保留原身份并归层，但不能自动触发无限的合同、审计、恢复与
状态发布链。

控制平面需要区分两个问题：

1. **这个声明是否已经资格化？**
2. **现在最有利于完成用户目标的合法下一步是什么？**

前者由证据与合同裁决；后者必须同时考虑业务目标、剩余义务、风险、预算和人类授权。二者相关，但不是同一个函数。

这不削弱任何已经声明的资格门。某项声明没有完成自己的门，就不能被写成已经资格化或已经生效；全局活性也不能成为
跳过 Gate、拼接 world、覆盖首败或降低 oracle 的理由。这里限制的只是另一种越权：资格链可以阻止相应声明升级，却不能在
没有新的目标、预算与人类决定时，自动取得整个项目路线的无限调度权。

## 6. 需要增加的不是新插件，而是全局进展不变量

这份反思不建议现在新增一个“活性插件”、新 Schema 或新资格门。那样很可能只是把“检查是否陷入检查循环”再变成一条可以
无限延长的检查链。

真正需要审议的是一个由控制平面和人类共同维护的**全局进展不变量**。post-R1 全局检查可以先把下列问题作为
falsifier checklist，检验现有方法是否存在合法但不终止的轨迹：

1. 它服务于哪个仍未履行的产品义务？
2. 当前阻塞这个义务的事实是什么，事实层级是什么？
3. 动作完成后，究竟减少了哪一个真实产品缺口或必要资格缺口？
4. 它是否会生成比消除的义务更多的新义务？
5. 本轮最多投入多少时间、尝试次数或外部调用？
6. 预算耗尽时进入哪个明确终态？
7. 如果出现反例，击穿的是哪个最小前提；为什么需要重开该边界？
8. 当前动作是否仍在回答用户最初的问题，还是已经悄悄更换了证明对象？

如果这些问题没有答案，继续施工本身就不是进展证据。但这份问题清单本身也不是新的 executable Gate，不要求每次动作都
追加文档、状态发布或资格链。它首先用于人工识别目标漂移；是否需要形成机器可执行合同，必须由真实反例和独立授权决定。

## 7. 有限终态必须是一等公民

一个长期任务不应只有“成功”和“继续工作”两种状态。至少需要允许以下有限终态：

> 下列名称只是概念示例，不是 VeriTrail 当前已经存在的 public status、Schema enum 或冻结 marker。

- `QUALIFIED_SUCCESS`：声明和产品义务均按约成立；
- `SAFE_INCOMPLETE / NOT_PROVEN`：没有越权或伪造，但在既定预算内无法证明；
- `BLOCKED_REQUIRES_HUMAN`：需要人类改变目标、风险容忍、资源或授权；
- `FAILED_WITH_PRESERVED_EVIDENCE`：真实失败已保留，当前最小边界被击穿；
- `CANCELLED_BY_HUMAN`：人类明确停止，不得伪装成成功。

永久 `IN_PROGRESS` 不是一个合法的隐藏终态。持续工作必须有剩余预算、明确进展和可检验的停止条件。

`SAFE_INCOMPLETE / NOT_PROVEN` 也不是成功的别名，更不授予 Agent 单方面放弃已获授权任务的权力。只有预算 owner 或明确的
阻塞合同允许停止时，它才能成为诚实终态；否则 Agent 仍须在既有 authority 内寻找有界替代路径，或把需要改变目标、预算、
风险容忍和授权的决定交还给人。

## 8. 目标与预算由谁拥有

全局进展不能由一个新的超级组件单独裁决。更稳妥的 authority 划分是：

| 主体 | 在本问题中的责任 | 不拥有 |
| --- | --- | --- |
| 人类授权者 | 选择产品目标、风险容忍、总预算、停止或继续，以及可接受的不完整终态 | 世界真相、Provider 未观察到的事实 |
| Reality | 现实中实际发生的事实 | 项目目标、合同或 Verdict |
| Provider | 自己实际观察到的事实及来源 | 全局充分性、项目优先级、Core Verdict |
| Core | 按 sealed contract 裁决证据完整性、绑定、充分性与确定性结果 | 现实事实、产品目标、施工预算 |
| Q / 调度能力 | 在明确授权后有界调度已经声明的证明义务 | Gate 定义、充分性、目标改写、`SAFE_TO_SKIP` 或 Verdict |
| Agent | 在当前 authority 和预算内选择、执行并报告有界动作 | 自我授权、静默改写目标、把忙碌声明为进展 |

Business Layer 可以组织流程、选择能力、减少无效重复和请求补充条件，但不能取代 Core 宣布证据已经足够。Core 也不能因为
拥有充分性裁决权而取得业务目标或项目调度权。目标、事实、充分性与执行预算必须继续由不同 owner 承担。

人类可以显式修改目标或预算，但修改后的任务是新的控制输入，不能倒写既有失败、冻结事实或历史资格。Agent 发现前提冲突时
必须报告；既不能以“人负责前提”为由沉默，也不能自行替人改变前提。

## 9. 对 Agent 行为的直接要求

用户指出错误时，反馈应当被理解为原任务的约束更新，而不是开启一个与原目标脱离的“纠错表演”。每次修正都需要同时检查：

- 原始目标是否仍被保持；
- 已经成立的部分是否遭到破坏；
- 当前错误是否真的消除；
- 整体成果是否更接近完成；
- 连续局部修补是否已经失效，是否需要重新检查前提或改变方法。

这可以压缩为两句话：

> 以目标连续性约束局部纠错，以实际成果检验任务推进。

> 不是下一次更会解释为什么错了，而是下一次真正做得更对。

## 10. 对 VeriTrail 的后续检查范围

当前 R1 不应因这份反思而改变既有施工边界、门禁、失败身份或授权顺序。R1 应继续按照已经建立的证据反馈工作法完成自己的
资格闭环。

R1 完成以后，应当独立进行一次**覆盖整个 VeriTrail 项目**的全局组合与活性检查。它不是只审 R1，也不是把历史测试和门禁
机械地全部重跑一遍，而是从产品目标、真实用户链和当前 exact public claims 出发，重新核对各阶段已经证明什么、组合后是否
仍然成立、哪些结论只在原局部世界中成立，以及哪些问题仍为 `UNKNOWN`。

“覆盖整个项目”不等于宣布全部冻结历史失效。既有失败、资格和冻结 identity 继续保持原事实；检查的是它们在当前整体中的
有效边界、组合关系和产品意义。只有真实反例击穿相应前提时，才重开最小必要边界。

### 10.1 检查对象

检查至少覆盖：

- 产品北极星、真实用户任务、当前产品声明和明确 non-goals；
- Core、入口层、P、R、Q 蓝图及其他已经出现的能力边界；
- public Schema、Artifact、Provider、handoff、Core Verdict 与人工 authority 的实际组合关系；
- 已发布 tag、Release、公开资产、README、project-state、能力地图与当前源码之间的投影一致性；
- 代表性真实用户链、跨模块失败传播、恢复路径、预算、退出条件和残留 owner；
- 已冻结局部事实能否共同支持当前全局主张，以及局部之间仍未证明的 seam；
- 历史首败、`UNKNOWN`、显式延期、未实现能力和可能已经失去职责的脚手架。

它至少回答：

- 各局部 authority 是否组合成了真实产品能力，而不仅是相邻合同的集合；
- 失败、恢复、重新资格化与状态发布是否都存在有限上界；
- 控制平面是否可能把资格失败自动升级为无限项目工作；
- 是否存在“每一步都正确，但用户问题始终没有解决”的合法执行轨迹；
- 哪些判断必须由人类作出，哪些可以由 Core、Q、Provider 或 Agent 机械执行；
- 产品义务、证明义务与施工义务是否被明确区分，并且能够分别终止；
- 当系统只能得到 `UNKNOWN` 或 `NOT_PROVEN` 时，是否可以安全、诚实、有限地停下来；
- 局部冻结事实是否真的支持全局产品主张，还是只支持更窄的历史结论。
- 全局检查自身是否具有明确范围、预算和退出条件，还是正在成为新的递归证明义务。

这次检查不能预设“现有方法一定有问题”，也不能预设“所有局部 PASS 必然组成全局 PASS”。它必须把二者都当成待验证命题。

### 10.2 人工与 AI 的共同检查

这项工作必须由人工与 AI 共同完成，但双方职责不同：

```text
AI
    -> 重建 exact facts、依赖图、失败链与 public claims
    -> 搜索逻辑漂移、遗漏 seam、循环恢复和局部/全局反例
    -> 执行获得授权的有界复核并保留完整证据

Human
    -> 确认产品目标、真实价值、风险容忍和检查预算
    -> 判断哪些 UNKNOWN 可以接受，哪些问题必须继续解决
    -> 决定是否重开边界、改变路线、停止投入或形成新的 Seal

Human + AI
    -> 共同选择需要验证的全局命题
    -> 共同解释反例，但不覆盖原始事实
    -> 共同形成有 owner、有预算、有退出条件的后续判断
```

这不是“AI 给出结论、人工签字”，也不是“人工给出直觉、AI 寻找支持材料”。AI 不能自己认证全局完成；人工判断也不能替代
exact evidence、Core 充分性裁决或真实产品观察。双方应当互相形成反例来源和纠偏机制。

### 10.3 预期产物与停止线

检查的产物首先应是：

- 一份绑定 exact 坐标的当前全局能力与用户链地图；
- 一份区分成立事实、组合缺口、真实矛盾、可接受 UNKNOWN 与未授权方向的核账结果；
- 一组按产品价值、风险和证明必要性排序的最小后续问题，而不是自动生成的新路线图；
- 明确记录哪些既有边界无需修改，以及为什么；
- 检查自身的预算、结束条件与人工最终裁决。

该检查只有在 R1 完成后、由人类明确确认范围与预算时才启动。它不自动启动 R2–R6，不因发现问题自动获得修复权，也不能把
“需要继续检查”作为永久不结束的默认结果。

## 11. 总结

VeriTrail 需要同时抵抗两种失败：

1. 把执行、绿色测试或漂亮解释冒充为现实完成；
2. 为了避免第一种失败而陷入无穷补证、无穷恢复和永久不交付。

前者要求证据反馈、冻结边界和严格 authority；后者要求目标连续性、全局进展不变量、有限预算和诚实的终态。

最终应当坚持：

> 以目标连续性约束局部证明，以有限终态检验全局进展。

这份反思的职责只是防止这个问题被遗忘，并为 post-R1 的独立全局检查保留清晰的问题定义。它本身不证明问题已经解决，
也不授权任何当前尚未获准的实现。
