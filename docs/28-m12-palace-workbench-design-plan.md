## 1. 本计划解决什么

M12 不是给现有 Workbench 换一套红金皮肤，也不是继续修补 M3 时期形成的页面构图。它要在
M0-M11 的事实、数据和用户任务完全不变的前提下，从信息空间开始重构 VeriTrail 的表现系统，形成
只属于“验迹”的故宫主题。

核心关系不是“现代工作台为体、故宫为用”，而是：

```text
证据关系决定空间
  × 故宫章法组织空间
  × 真实内容检验空间
  = VeriTrail 的表现系统
```

布局为了显示事实；真实事实进入后，又必须反向证明布局不是空洞形式。任何只在空白 Mock 或精选
截图中成立、放入长哈希、失败状态、矩阵和原始证据后就崩溃的设计，都不算完成。

## 2. 已确认的设计决策

以下决定来自 M12 实施前讨论，计划确认后不得在编码时静默改变：

1. 不继承 InkNarratives（墨叙）的叙事阅读气质，也不继承 DarkRoomLibrary（暗室藏书）的暗室与藏书
   空间气质；两个项目不作为 M12 构图母版。
2. M11 Workbench 不被否定，而是冻结为功能与交互控制组。M12 可以抛弃其视觉外壳，但不能抛弃其
   已证明的工程事实。
3. M12 是表现系统重构，不是局部美化。允许调整组件组合、DOM 分组、信息顺序、响应式布局和焦点
   路径，因此范围为 `L0 + bounded L1`，不再错误地标成纯 L0。
4. 故宫主题来自北京中轴线的空间秩序与明清紫禁城的建筑章法、矿物色彩、院落层次和礼序；不把
   整体做成宋画，也不把 UI 论证扩大成需要额外证明的历史谱系命题。
5. 中国审美的“留白不死、虚实相生”仍是约束，但 M12 的空不是纸面雾白，而是被门、墙、台基、
   轴线和重色建筑撑起的“院落之空”。
6. 不使用整体低对比、灰雾、柔焦、奶油白、雾青或统一色温制造泛化的“东方高级感”。主题应有
   黑白、朱、黄、青、绿之间受控的内部张力，保持活气。
7. 不以屋檐、祥云、龙纹、印章、仿古纹理或栏目改名证明故宫。现有“午门、四象殿、万象院”等
   别名若保留，只能作为不影响扫描的次级文字，功能名称始终是第一信息。
8. 不贴背景图，不使用装饰位图、远程字体、CDN、遥测或第三方主题资产。证据截图是被验数据，
   不属于装饰资产。
9. 顶层模块导航使用可收拢的十字中轴导航；它是空间骨架，不是悬浮装饰，也不承载无限增长的 Run。
10. 精确色值、比例和局部密度必须在真实浏览器与真实 M11 数据中验证后才能冻结，颜色名称和计划
    文字不能代替显示事实。

## 3. 控制变量与基线

### 3.1 控制组

- 代码与功能基线：`m11-v0.12.0`；
- 同一 Python Core、只读 API、Vue 数据 Loader、Schema 与确定性 Verdict；
- 同一 M11 Gate B 四个真实 Run、一个隔离损坏包和正向恢复 Comparison；
- 同一正向、负向、损坏 Bundle，以及 Pairing 和 Batch 脱敏夹具；
- 同一桌面/移动浏览器、视口、数据文件、网络边界和测试步骤。

M12 不在生产界面加入主题切换器。旧界面由冻结标签单独构建作为控制组，避免为了比较而增加新的
运行时状态和维护面。

### 3.2 主要变量

里程碑级唯一主要变量是：

> `workbench_presentation_system = palace_evidence_m12`

实现期仍按切片控制变量：每个切片一次只替换导航、空间骨架、令牌、某一类视图或响应式规则中的
一组，完成回归后再进入下一组。不得把全部 CSS、DOM、交互和文案一次性混改后只做最终截图。

### 3.3 保持不变

- Bundle/Manifest/Evidence/Report 的读取、哈希与交叉引用校验；
- ExecutionStatus、Verdict、Comparison、Pairing、Batch 的全部语义；
- Catalog 与 API 的只读边界；
- 本地文件只读导入、对象 URL 回收和损坏包隔离；
- URL、刷新、后退、前进和 Catalog 返回焦点的既有用户事实；
- M0-M11 的 `data-testid` 行为合同，除非先建立消费者迁移表并证明只是表现层重命名。

## 4. 范围与禁止项

### 4.1 允许变更

- 页面信息架构与视觉优先级；
- `App.vue` 和现有视图组件的表现性组合与语义化 DOM；
- 顶层十字导航及其键盘、触控与焦点行为；
- CSS 令牌、空间、排版、边界、状态外观、动效和响应式规则；
- Catalog、Run、Comparison、Pairing、Batch、Browser Evidence 的表现组件；
- 加载、空、错误、损坏、无 Browser Evidence 等适用状态；
- 为表现组件增加的局部测试与浏览器验收脚本。

### 4.2 明确禁止

- 修改任何 Python Schema、Verdict、Evidence、Catalog 或 Comparison 生产逻辑；
- 在前端重新裁决、合并 ExecutionStatus/Verdict，或把自报状态冒充 Core 重推导；
- 新增计划编辑、在线写、Run 启停、命令执行、报告发布、登录或云端能力；
- 为布局方便删减必要证据、截断失败事实或隐藏适用边界；
- 新增第二套业务数据模型、全局状态库或路由框架；
- 用截图、Mock、组件测试或构建通过代替真实工作台链路；
- 借 M12 处理 M13 的全仓结构重构，或提前实施 M13/M14。

实际 diff 一旦触及 L2/L3，立即停止 M12，列出消费者和爆炸半径，不能以“只是前端”降级审查。

## 5. 顶层十字中轴导航合同

### 5.1 信息映射

十字导航只承载四类数量固定的公共视图；Run 详情、原始证据和 Browser Evidence 继续从 Runs 内部
进入，不把无限条目塞进十字结构。

```text
                         Runs / Catalog
                               ↑
Paired Analysis      ←      当前中枢      →      Batch Analysis
                               ↓
                       Rerun Comparison
```

- 北向 `Runs`：权威 Run Catalog、本地 Bundle 和 Run 详情入口；
- 南向 `Comparison`：两个同计划 Run 的确定性复跑比较；
- 西向 `Pairing`：四角色预注册配对/反事实分析；
- 东向 `Batch`：全因子矩阵与固定种子批次分析；
- 中心：显示当前视图身份，并负责展开/收拢，不制造第五类业务事实。

南北轴表达“来源 Run -> 直接复跑比较”，东西两翼表达更复杂的多 Run 分析。四向含义在所有页面、
视口和状态中保持不变。

### 5.2 形态

- 收拢时仍显示“目录”和当前视图，不做只有作者才懂的神秘图标；
- 十字在正常文档流中占有稳定尺寸，不使用会遮挡 Verdict、内容或移动端安全区的浮动按钮；
- 展开前后容器尺寸稳定，内容不得因标签长度、图标或状态变化发生跳动；
- 南北轴可以比东西轴更强、更长，避免变成四向完全等权的游戏手柄；
- 形态依靠 CSS 网格、边界、色块和层级，不绘制仿古屋顶或遥控器写实外壳；
- 选择目标后收拢，并把焦点移动到目标视图的主标题；浏览器后退/前进恢复正确视图。

### 5.3 键盘、触控与辅助技术

- 中心必须是原生 `button`，使用 `aria-expanded` 和 `aria-controls`；
- `Enter/Space` 展开或收拢；`Esc` 收拢并把焦点还给中心；
- 展开后同时支持 `Tab` 的正常顺序与方向键的空间移动，不能强迫用户猜测按键模式；
- 收拢时四个入口不可见、不可聚焦，也不进入屏幕阅读顺序；
- `Tab` 顺序固定为中心、北、东、南、西；方向键按几何位置移动；
- 每个入口有短功能名称，图标不能成为唯一名称；陌生图标必须有可访问名称。tooltip 只作为可选
  辅助说明；若存在，必须同时支持 hover 与 keyboard focus，且不能成为理解功能的必要条件；
- 触控目标至少 44 x 44 CSS px，不依赖 hover，不因手指遮挡丢失当前状态；
- `prefers-reduced-motion` 下取消非必要展开动画；普通展开反馈控制在约 150-220 ms；
- 页面不增加可见的键盘教学文案，交互应通过标准控件、焦点和空间关系自行成立。

## 6. 信息空间与视图章法

### 6.1 Runs / Catalog

- 顶层目录不再使用等权卡片墙；桌面使用可扫描的档案簿/行式目录，移动端变为单列记录；
- Run ID、ExecutionStatus、Verdict、时间/计划身份和问题隔离保持稳定列序；
- `ABORTED + PENDING` 必须同时可见，不因行式密度压成一个状态；
- 进入 Run 后，Verdict 位于主轴，Plan/Profile、资源和适用边界作为支撑信息分列；
- 返回目录时恢复原 Run 焦点和滚动上下文。

### 6.2 Run 详情与原始证据

- 页面顺序固定为：身份/可信状态 -> ExecutionStatus/Verdict -> 原因 -> 断言 -> Browser Evidence ->
  Evidence Ledger -> 缺失/污染/适用边界；
- 不是把所有内容装进相同卡片，而是通过台基层级、轴线和疏密区分事实重量；
- 长 SHA-256、路径、错误信息和多行原因必须换行或在明确的局部滚动区显示，不能撑破页面；
- 原始证据区允许高密度，但不能与最终 Verdict 争夺第一视觉位置。

### 6.3 Comparison

- 两个来源 Run 左右或上下镜像，差异/一致结论处于共同轴线上；
- `MATCH / DRIFT / INCONCLUSIVE` 不复用 Run Verdict 的颜色或组件语义；
- 移动端由左右镜像转换为有明确来源顺序的上下结构，不丢失对照关系。

### 6.4 Pairing

- `BASELINE -> TREATMENT -> RESTORED_BASELINE -> NEGATIVE_CONTROL` 顺序不可被装饰打散；
- 初始与恢复基线应形成视觉呼应，但不能暗示实际值相同；
- 角色状态、预注册 outcome 与适用边界仍是独立层。

### 6.5 Batch

- 全因子矩阵本身承担格局，不再在表格外叠加多层卡片；
- 固定种子 wave、来源 Verdict 和 coverage/hypothesis 双状态必须分层显示；
- 小视口允许矩阵在具名 `role=region` 中局部横向滚动，但页面根节点不得横向溢出；
- 4-16 格、缺格、不符和来源失败状态均进入真实验收。

### 6.6 Browser Evidence

- 步骤时间线、Console、Network 和截图仍使用标准 tab 语义；
- tab 组必须以明确成组、选中态和焦点环解释方向键行为，同时保留 `Tab` 进入/离开控件组；
- 截图对话框关闭后恢复触发元素焦点；空 Browser Evidence 不伪装成错误；
- Console/Network 的失败事实不能因主题色或折叠默认值被弱化。

## 7. 故宫空间与色彩合同

### 7.1 空间气韵

- 宏观轴线稳定，局部视图根据证据类型变化，避免所有页面复制同一模板；
- 空白是院落、台基和转场，不是无边界大白页；重色结构必须给空白提供边界和重量；
- 疏与密、冷与暖、亮与暗、静态秩序与交互开合共同形成活气；
- 不使用模糊、磨砂、雾层、渐变光斑或整体降饱和掩盖层级问题；
- 第一视口直接呈现真实工作台，不制作营销落地页或解释性 hero。

### 7.2 色彩双层职责

M3 的 `--paper / --jade-white / --wall-red` 等令牌只作为历史控制组，不自动继承。M12 先冻结语义角色，
再通过真实浏览器确定色值：

| 层 | 角色 | 使用边界 |
| --- | --- | --- |
| 建筑结构 | 深宫墙朱/漆红 | 固定品牌轴线或非交互结构；不得作为普通按钮、选中态或数据状态 |
| 建筑结构 | 琉璃黄/金 | 极少量高点、运行中或校验中；不能用于低对比正文或奢华渐变 |
| 建筑结构 | 石青/石绿/黛色 | 导航、边界、分区与冷色制衡，避免红金单调 |
| 建筑结构 | 汉白玉/青灰砖/墨 | 大阅读面、院落空间、正文和高密度证据 |
| 证据语义 | FAIL/ERROR 警示朱 | 只随状态出现，必须同时有文字、图形、位置和边界差异 |
| 证据语义 | PASS 玉石绿 | 只表达通过，不装饰普通区域 |
| 证据语义 | PENDING/ABORTED | 分别使用灰阶与形状/标签，不互相吞并 |
| 证据语义 | INCONCLUSIVE | 使用独立石青语义，不冒充信息提示 |

结构朱与失败朱必须是不同 token、不同位置、不同触发机制。若真实浏览器验收仍会误判，语义警示优先，
必须削弱或移除结构朱，不能为了“像故宫”牺牲证据判断。

精确色值只有同时满足以下条件才能进入最终 tokens：

- 普通文本 4.5:1，大字和非文本交互边界 3:1；
- PASS/FAIL、ABORTED/PENDING、MATCH/DRIFT 在灰度和色觉差异下仍可辨；
- 桌面、移动和系统缩放下不出现大片单一米黄、红金或黛青主题；
- 实际截图中白仍是白、墨仍有重量、矿物色仍明确，不被统一雾化。

### 7.3 排版、边界和材质

- 标题可使用本机中文衬线回退栈，正文使用系统无衬线，哈希/结构数据使用等宽字体；
- 不按视口宽度连续缩放字体；紧凑面板标题不得使用 hero 字号；
- 字距保持 0，不用负字距制造仿古感；
- 卡片只保留给真正重复的记录或模态工具，禁止页面段落漂浮卡片化和卡片套卡片；
- 圆角不超过 8 px，结构主要依靠轴线、细边、台阶式层级和色块；
- 不新增图标依赖作为默认方案；确需新增时必须单独审查离线、体积、许可和可访问性，不能手绘 SVG
  或用生僻字符代替标准控件。

## 8. 响应式与内容压力矩阵

正式实现至少覆盖以下串行视口，不在 16 GB 主机上无界并行 Chromium：

| 视口/模式 | 目的 |
| --- | --- |
| 1440 x 960 | 主桌面完整链路与信息密度 |
| 1280 x 800 | 窄桌面、长导航和边界压力 |
| 1024 x 768 | 轴线折叠与双栏退化 |
| 390 x 844 | 主移动验收 |
| 360 x 800 | 小屏、长词和十字触控压力 |
| 桌面 200% zoom | Reflow、焦点与文本放大 |
| `prefers-reduced-motion` | 非必要动效关闭 |
| `forced-colors: active` / Windows High Contrast | 证明状态仍由文字、图形、位置和边界表达，不依赖主题色 |

每个适用视图必须加入：最长 Run ID/SHA、中文和英文长词、`ABORTED + PENDING`、空列表、加载、损坏
Bundle、Browser 不适用、Comparison DRIFT、Pairing INCONCLUSIVE、Batch 缺格和 16 格矩阵。

根页面横向溢出必须为 0；只有明确标注且键盘可聚焦的矩阵/高密度区域可以局部滚动。任何文字、按钮、
状态徽章、十字导航臂或截图不得互相遮挡或改变固定控件尺寸。
