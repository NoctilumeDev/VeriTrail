# VeriTrail 产品目标、权威边界与演进原则

> 文档性质：长期产品与架构原则，非状态声明，非冻结合同，非 Roadmap，非施工授权。
>
> 本文承担“稳定方向”的作用，但不使用“北极星”作为正式名称。比喻容易把长期目标、演进路线和当前施工许可混在一起；本文用可核对的责任与边界直接表述。

## 1. 本文解决什么，不解决什么

VeriTrail 已经形成一套严格的工程证据与资格方法，但插件、Provider、分析器和调度器越多，越容易把内部能力的建设误当成产品目标本身。

本文只回答四个长期问题：

1. VeriTrail 最终要为用户解决什么工程问题；
2. Reality、Human、Provider、Core、业务组织与行动能力分别拥有什么权威；
3. 局部能力怎样通过有限真实场景持续获得端到端反馈；
4. 长期方向怎样与当前状态、成熟度路线和施工授权保持分离。

本文不回答“下一项实现任务是什么”，也不声明任何候选能力已经实现、资格化、冻结或发布。当前事实必须从 exact main、冻结合同、保留证据、资格链、当前状态文档和 fresh installed-product observation 重建；文档顺序、路线优先级和本文内容都不是调度器。

若本文与已冻结合同或已资格化事实发生冲突：

- 对当前实现与裁决，已冻结合同和保留证据优先；
- 对长期产品方向，应显式修订本文，而不是静默改写历史合同；
- 对下一步施工，必须重新进入 CONTROL LOOP 并取得本阶段的明确授权。

## 2. 产品目标

VeriTrail 面向的不是某个插件，而是用户提出的工程问题：

> 给定一个明确目标、可封存的验收条件和实际取得的证据，系统应判断当前证据能够支持什么结论，暴露缺口、冲突与不确定性，并让人能够复查、复验和作出最终处置。

第一阶段完整产品闭环止于：

1. 验证声明；
2. 发现异常；
3. 定位故障；
4. 在证据允许的范围内归因；
5. 修正后复验确认。

VeriTrail 不是“测试全绿展示器”，也不是插件集合、日志大屏、AI 裁决器或自动修复平台。测试、CI、浏览器、日志、运行指标和外部平台都可以提供证据，但任何单一来源都不能自动替代封存合同要求的完整证明义务。

长期优化目标始终是：

> 在不改变证明义务、不越过权威边界、不隐去不确定性的前提下，更可靠、更高效地回答用户的工程问题。

插件、Provider、分析器和调度器的价值，只来自它们对这个目标的贡献，而不是它们自身的存在。

## 3. 权威模型

### 3.1 Reality 不是软件组件

现实事实由 Reality 拥有。任何系统都只能在特定条件下观察现实，不能因为保存了大量 Evidence 就成为“现实事实的拥有者”。

### 3.2 责任与权威

| 主体 | 拥有的权威 | 明确不拥有 |
| --- | --- | --- |
| Reality | 现实中实际发生的事实 | 软件合同、裁决规则或产品状态 |
| 用户 / 人类授权者 | 目标、验收前提、风险处置，以及合同要求的 Seal 决定 | 改写既有 Evidence、跳过证明义务或手工制造 `PASS` |
| Provider / Evidence Producer | 在声明的方法、条件、时间和来源下，自己实际观察到什么，以及该观察的 provenance | 世界终极真相、验收标准、完整分母或最终 Verdict |
| R / Q / O / T | 各自冻结合同内的审查、调度、观察或测试证据职责 | 跨轨全局权威、Core Verdict 权或未获授权的行动权 |
| Business Layer | 业务流程组织、能力选择、先后与并行、采集预算、用户交互和补充条件请求 | 证据充分性裁决、证明义务修改或最终 `PASS` |
| Core | Evidence 身份、完整性、绑定、冲突、充分性和确定性裁决；按封存合同计算 Verdict | 现实真相、业务目标的所有权、外部执行资源或人工最终处置 |
| Action Layer | 在独立安全边界和明确授权下修改代码、部署、重启、回滚或执行其他有副作用的动作 | 因诊断能力存在而自动获得行动许可 |

Provider 的权威应准确表述为“观察证明”而不是“事实所有权”。它能够证明：在某个版本化采集方法、输入、时间和环境中，它观察到了某项结果；它不能单独证明未观察到的事实不存在，也不能把自己的投影提升为完整现实。

### 3.3 Core 不是超级组件

Core 不应成为拥有所有事实、业务语义、执行资源和工作流的超级组件。它只在 sealed Plan / Acceptance Contract 与标准 Evidence 相遇的边界内执行确定性核验。

因此：

- Core 不替 Provider 观察外部世界；
- Core 不替 Business Layer 组织用户流程；
- Core 不替人决定最终是否交付、接受风险或继续投入；
- Core 不因为“信息很多”就推断没有证据支持的现实；
- Core 必须把 `UNKNOWN`、`INCONCLUSIVE`、`PENDING`、冲突和缺失保留下来。

### 3.4 Business Layer 不是隐性裁决器

Business Layer 可以决定：

- 为解决当前任务需要哪些能力和 Provider；
- 先检查什么，哪些任务可以并行；
- 何时继续采集，何时停止重复采集；
- 何时需要用户补充目标、条件或风险决定；
- 如何把内部 R / Q / O / T 能力组织成用户可理解的流程。

它不能自行宣布“证据已经足够，所以 `PASS`”。

Business Layer 可以停止采集，但停止采集不会消灭尚未履行的证明义务。若 Core 仍观察到缺口，结果必须保持为相应的 `PENDING`、`INCONCLUSIVE`、`UNKNOWN` 或其他合同规定状态，而不是由编排器降低标准。

## 4. Business、Q、Provider 与 Core 的协作协议

建议的长期协作关系是：

```text
用户工程目标
    -> 候选声明与业务不变量
    -> 人确认并封存验收合同
    -> Core 展开证明义务与未满足项
    -> Business Layer 组织业务流程和能力选择
    -> Q 在不改变义务的前提下安排顺序、并行与安全复用
    -> Provider 在各自条件下产生带 provenance 的观察
    -> Core 重新核验证据绑定、完整性、冲突与充分性
    -> 人读取结论与边界，作出最终处置
```

这条链有四个硬约束：

1. Business Layer 不能替 Core 缩小证明分母；
2. Q 只能优化既定证明义务的执行成本，不能跳过 Gate、弱化 Oracle 或改变 Verdict 语义；
3. Provider 只能报告自己的观察，不能把局部成功提升为全局完成；
4. Core 只能按已封存规则裁决，不能替人补写未确认的业务目标。

## 5. 两种用户体验

### 5.1 面向任务的产品体验

普通用户不应先理解 R / Q / O / T、Provider 数量或内部 stage graph，才能提出问题。产品入口应围绕用户任务组织：

- 我想验证什么声明；
- 哪些前提必须成立；
- 当前还缺什么证据；
- 哪个环节发生了异常；
- 结论为什么成立或为什么暂时不能成立；
- 修正后怎样复验。

内部能力可以被组合、替换或演进，但不应迫使用户以插件结构描述自己的工程问题。

### 5.2 专业 Evidence Workbench

现有 Workbench 不应被删除。它应继续作为专业证据阅读器，允许审查者展开：

- sealed Plan / Acceptance Contract；
- 原始条件、版本、环境和资源边界；
- Provider provenance 与采集方法；
- 源码、执行、浏览器、测试和平台观察；
- Evidence 绑定、冲突、缺口和裁决依据；
- 历史 Run、失败、复验与适用边界。

“面向任务的简洁入口”和“可下钻的专业证据面”不是二选一。前者降低使用门槛，后者保留可复查性；两者都不能在展示层重新裁决。

## 6. 自动修复与行动能力

诊断能力不自动产生行动权。

修改代码、部署、重启、回滚、写数据库或改变生产配置，都应属于独立 Action Layer，并具有自己的：

- 明确授权主体；
- 作用范围与副作用边界；
- 预览与确认；
- 资源、安全与回滚条件；
- 执行回执与 Evidence；
- 修正后的重新验收。

第一阶段的核心产品闭环可以告诉用户“哪里有问题、证据是什么、修正后是否恢复”，但不能因为系统知道一种修法，就自动获得执行该修法的权限。

## 7. 演进与集成原则

### 7.1 不等全部能力完成后才第一次集成

单个插件或能力通过自己的合同，只证明它在自己的责任范围内成立。多个能力能否共同回答真实业务问题，是另一项需要独立证据的问题。

因此长期演进节奏应是：

```text
能力局部闭环
    -> 有限真实业务场景集成
    -> 发现跨能力问题
    -> 只重开被反例击穿的最小边界
    -> 继续演进
    -> 在证据充分后做全局收敛
```

这不等于现在启动一个全能 Business Orchestrator。早期集成首先是一种反馈机制，用来发现责任缝隙、共同模式失败、分母漂移、跨阶段错绑和用户体验断层。

### 7.2 全局优化必须受约束

最终可以优化端到端时间、重复采集、资源消耗和用户交互，但任何优化都必须同时满足：

- 不改变 sealed proof obligations；
- 不缩小适用分母；
- 不让多个组件共享同一错误 projector 而互相“证明”；
- 不用后继成功覆盖首个失败；
- 不把执行完成、局部测试通过或证据可显示误写成状态生效；
- 不把产品愿景当成当前施工授权。

### 7.3 成熟度路线不是施工 Roadmap

可以用以下成熟度层次理解长期演进，但不能按顺序自动施工：

1. **能力闭环**：每项能力在自己的合同、证据和失败边界内成立；
2. **参考场景集成**：有限真实场景暴露跨能力问题；
3. **业务组合合同**：对稳定出现的跨能力责任建立版本化合同；
4. **产品收敛**：把内部能力组织成围绕用户问题的体验；
5. **可选行动层**：在独立授权和安全边界下执行有副作用的动作。

每一层都只能在当时的 exact state 上重新审计、取得明确授权并完成自己的资格链。层次描述不授予任何实现权限。

## 8. 参考场景

参考场景是端到端反馈实验室，不是核心业务模板，也不是对当前 Roadmap 的承诺。

### 8.1 首个参考场景：AI 新增功能的系统级正确性

首个场景宜选择具有明确业务不变量、跨多个副作用、又能在本地受控环境中复验的真实功能。例如“订单取消”：

```text
用户取消订单
    -> 订单状态变更
    -> 库存恢复
    -> 支付退款
    -> 消息投递
    -> 系统级业务不变量核验
    -> 失败定位与证据归因
```

它不要求所有系统都同步成功，而要求计划明确：

- 哪些结果必须原子成立，哪些允许有界最终一致；
- 每个副作用的完成、待处理、失败和结果未知怎样表达；
- 库存、退款和消息是否具备 exactly-once 或幂等边界；
- 所有派生结果是否绑定同一次取消请求与同一业务对象；
- 超时、重试、恢复和补偿后，最终状态怎样复验；
- 缺少权威证据时为什么不能宣布全局成功。

这些领域语义应由场景适配器、命名断言和 sealed contract 提供，不能硬编码进 Core。

### 8.2 后续参考场景：跨浏览器与设备兼容

华为浏览器兼容可以作为后续独立参考场景，用于检验：

- 跨浏览器、设备和视口的证据采集；
- Console、Network、交互、截图和布局事实的绑定；
- 环境差异、能力缺失与真实产品缺陷的区分；
- 无法复现或观察不完整时的不确定性保留。

它同样不能仅凭截图相似或单次页面打开成功就宣布兼容。

## 9. 能力地图与部署基线

- R / Q / O / T 是职责轨，不是面向用户的产品菜单，也不自动等于四个固定部署单元；
- D / Cu 可以保留为候选能力地图位置，但在取得自己的问题、合同和资格以前，不应成为核心依赖；
- Business Layer 是责任边界，未来可以由多个组件共同承担，不预设一个新的中心化超级服务；
- 当前继续以 local-first 为部署基线；没有证据以前，不承诺云端多租户、组织级共享状态或集中式事实中心；
- 独立系统之间通过版本化合同、不可变 Artifact 和可替换 adapter 协作，状态所有权、凭据、执行入口和 Verdict 权不能因集成而跨界漂移。

## 10. 仍需独立回答的问题

本文故意不提前冻结以下机制：

1. 自然语言目标怎样转化为可封存业务不变量，以及用户在哪一层确认；
2. 多个 Provider 对同一对象给出冲突观察时，冲突身份、优先级和补证责任怎样表达；
3. Human Seal 具体确认的是合同、风险接受、证据处置还是行动授权，怎样避免一个 Seal 获得过宽含义；
4. Business Layer 停止采集时，怎样机械保留所有未满足证明义务及停止原因；
5. 参考场景何时产生可复用组合合同，何时只应保留为场景特有适配；
6. Action Layer 的预览、授权、回滚和复验怎样与 Core Verdict 解耦。

这些问题应通过独立审计、反例和版本化合同收敛，不能在本文中以愿景措辞提前取得实现事实。
