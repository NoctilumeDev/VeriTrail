# 00. 产品定义

## 1. 一句话定位

VeriTrail 是一个本地优先的全链路验收证据工作台：它用控制变量法组织实验，在明确的
资源与环境边界内收集自动化、浏览器和系统事实，并以确定性规则判断证据是否足以支持结论。

## 2. 目标用户

首批目标用户是：

- 在单台开发机上验证前后端或分布式系统的独立开发者；
- 需要把测试、F12、日志、数据库和资源事实汇总为验收结论的小团队；
- 希望区分“代码写完”“局部测试通过”和“真实系统完成”的工程人员；
- 在资源受限环境中采用串行、分批和缩比实验，但不愿降低一致性底线的人。

它不是某个仓库的附属脚本，也不预设 Java、Python、Go、Vue、MySQL 或某种消息队列。
项目专有语义通过适配器和用户断言进入，核心模型只处理实验、证据、资源与裁决。

## 3. 用户问题

现有工具通常分别回答某个局部问题：测试框架报告断言，浏览器记录网络，监控系统记录
指标，压测工具记录吞吐，数据库保存最终事实。但验收者仍需手工回答：

1. 本次运行相对基线到底改变了什么？
2. 其他条件是否真的保持一致？
3. “并发 1000”具体指什么负载维度？
4. 运行被资源停止线中止时，应该判失败、待定还是不可归因？
5. 自动化、真实浏览器和权威事实是否共同支持同一个结论？
6. 失败能否用相同代码、数据、拓扑、变量和随机种子复现？

VeriTrail 的工作不是收集更多日志，而是让这些问题成为实验计划的必填项和裁决规则。

## 4. 产品原则

### 4.1 控制变量优先

一个可归因实验只允许一个主要变量。代码版本、配置、数据集、实例拓扑、负载模型、
浏览器版本和资源预算应冻结为受控变量；无法固定的因素必须标记为干扰变量或未知变量。

如果多个主要变量同时变化，运行仍可保留，但结论必须是 `INCONCLUSIVE`，除非它本来
就是一个明确声明的组合交互实验，且基线与组合矩阵已经定义。

### 4.2 三类实验回答不同问题

1. **单变量串行**：证明某个组件、配置或故障究竟改变了什么。
2. **分批组合**：验证所有声明组合的交互；组合顺序可随机，但必须保存种子。
3. **代表性全链路**：在资源允许的最大有效组合上证明系统是否完整运行且不变量成立。

确定性矩阵先于随机扰动。随机测试用来寻找偶发问题，不能替代覆盖清单。

### 4.3 资源边界不是正确性折扣

- 资源预检失败或触发停止线时，中止运行、保存现场并标记 `ABORTED`。
- 不因机器较小而降低库存、账务、幂等、安全或其他硬性不变量。
- 容量结论只对声明的硬件、拓扑、版本、数据规模和负载语义有效。
- 每批结束必须确认进程、端口、容器、连接和临时数据是否释放，防止残留污染下一批。

### 4.4 核心事实与辅助能力分层

被测系统可以声明能力层级：

- **Hard invariant**：核心事实，不允许降级或静默丢失。
- **Bounded degradation**：辅助能力可以关闭、回源、延迟或限流，但必须有边界与证据。
- **Experience objective**：视觉、延迟或便利性目标，可以受环境影响，但不能掩盖硬性失败。

### 4.5 确定性机制保留裁决权

AI 可以在未来总结异常、聚类日志或建议下一步，但不能生成、覆盖或绕过 `PASS/FAIL`。
验收结论由版本化规则、不变量和证据清单计算。

### 4.6 分层审查控制爆炸半径

每个变更必须先声明影响层级：

| 层级 | 典型范围 | 最低验收要求 |
| --- | --- | --- |
| `L0_PRESENTATION` | 文案、样式、静态内容 | 真实浏览器、F12、视口与可访问性 |
| `L1_COMPONENT` | 单一组件/模块的私有实现 | 局部自动化、所有者边界与目标运行链路 |
| `L2_CONTRACT` | API、Schema、共享类型、公共配置 | 消费者矩阵、兼容性、契约回归和代表性全链路 |
| `L3_SYSTEM` | 数据所有权、状态机、一致性、安全、全局策略 | 系统影响图、多实例/故障/恢复和完整不变量验收 |

实际 diff 触及更高层时必须升级审查，不得继续用低层证据结案。局部需求不应通过修改全局
序列化、共享配置或公共模型来“快速解决”；确需全局变化时，全部下游消费者都进入验证范围。

### 4.7 里程碑先闭环再演进

下一里程碑可以提前研究与规划，但前一里程碑未取得代码事实、自动化证据和真实运行证据，
并冻结为可寻址基线前，不得进入实现。资源不足只会让当前里程碑保持 `PENDING`，不能成为
跳过门禁的理由。

这样可以防止早期接口、状态机或所有权未稳定时继续叠加功能，最终出现牵一发动全身的返工。

### 4.8 预注册、重复与反事实

实验开始前冻结计划版本、变量、断言、停止线、清理步骤和裁决规则。观察结果后修改标准必须
创建新计划版本，保留旧运行与修改理由，避免移动目标、选择性报告或事后制造 `PASS`。

重要结论应能重复。适用时使用“基线 -> 处理 -> 恢复基线”的配对运行：效果随主要变量
出现，并在变量撤销后消失，因果解释才更可信。性能和偶发故障需要多次运行与分布事实，
不能用一次最优结果代表整体。

### 4.9 证据有效期与观察者效应

基线必须声明有效条件。代码、配置、依赖、数据、拓扑、浏览器或规则越过容差时，旧结论
标记为过期，不能自动担保新版本。

VeriTrail 自身的 CPU、内存、连接、磁盘与采样开销单独计量。采集器显著改变负载或时序时，
报告必须说明观察者效应，必要时降低采样率或进行无采集对照运行。

## 5. v0 用户闭环

一个用户应能完成：

1. 创建实验计划并选择或生成基线。
2. 定义一个主要变量、受控变量、资源预算、负载语义、不变量与停止条件。
3. 执行或导入一次运行，获得环境、自动化、浏览器和系统事实。
4. 查看证据缺口、变量漂移、资源停止和不变量结果。
5. 得到 `PASS / FAIL / INCONCLUSIVE / PENDING` 之一，并理解原因。
6. 导出带清单、哈希、版本、种子和适用边界的 Markdown/JSON 证据包。
7. 以相同计划复跑或与基线比较。

## 6. v0 范围

### 必须包含

- 实验计划与基线；
- 变更影响层级、消费者矩阵与里程碑依赖门禁；
- 变量分类和漂移检测；
- 资源预检、软/硬停止线和中止现场；
- 明确的负载语义模型；
- 浏览器 Console、Network、截图与步骤证据；
- 通用文件/HTTP/进程/断言导入；
- 确定性裁决与证据缺口说明；
- 本地持久化、哈希清单和报告导出；
- 一次轻量项目的真实自举验收。

### 明确不做

- 通用 CI/CD 平台、APM 或日志平台替代品；
- 云端多租户服务；
- 默认依赖 Docker 或大型中间件；
- 任意 Shell 执行器；
- 为特定业务、语言或消息队列硬编码工作流；
- AI 自动修复、AI 裁决或无证据的自然语言结论；
- 在 v0 宣称生产容量或企业级安全认证。

## 7. 成功标准

v0 成功不以集成数量衡量，而以闭环衡量：

- 同一计划可以复跑并生成可比较证据；
- 计划在运行前封存，修改后形成新版本；
- 重要结果可通过重复、配对或反事实运行验证；
- 单变量实验能够指出变化与基线差异；
- 多变量污染会被阻止或标记为 `INCONCLUSIVE`；
- 资源中止与业务失败不会混为一谈；
- 浏览器与自动化证据冲突时不会静默通过；
- 报告能回答“结论、依据、边界、复现方式和缺失证据”；
- 旧基线失效时结论会过期，工具自身开销不会混入被测对象指标；
- 项目自身通过真实浏览器与证据包完成一次自举验收。

## 8. 来源案例与通用化

PlainJournal 的受限单机实验提供了重要问题样本：中间件分批、固定种子随机顺序、五类故障、
负载语义、资源停止线、幂等和最终一致性。但这些只用于验证通用模型是否表达力足够。

核心模型不得出现订单、库存、支付、RocketMQ 等必填概念。类似事实应由被测项目以
命名断言、适配器或证据导入的形式提供。未来同一套模型应能表达静态前端、REST API、
桌面工具、游戏服务、数据管道和分布式系统。
